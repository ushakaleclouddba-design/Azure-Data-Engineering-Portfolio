# Architecture Board Guide

> A self-explanatory companion guide for the SQL Server → Azure Migration Assessment.
> Written so that someone who has never seen the tool before can open the report and understand both **what they're looking at** and **how to interpret what they see**.

> **Scope note:** This is Phase 1 of a two-phase POC. Phase 1 is an **AI-augmented assessment and recommendation tool** — deterministic pipeline with an LLM at three decision points. Phase 2 (in development) adds a genuine agentic layer on top of this output. When this guide says "the agent," it refers to the Phase 1 tool unless otherwise noted.

---

## 1. Executive Summary

This document accompanies the Migration Assessment Report (Excel workbook) produced by an AI-augmented SQL Server-to-Azure migration assessment tool. The tool answers a specific question that DBAs and architects keep asking by hand: given a SQL Server estate, which Azure migration target makes sense for each server, what does each option cost over a year, and which findings would block or complicate the migration.

The report is intended to be self-defensible. Every cost number traces to a documented source. Every recommendation is generated by a large language model reasoning over real assessment data and live Azure pricing — not over canned rules. Readers can follow any number, any recommendation, and any conclusion back to its inputs.

### What this tool does

- Connects to a SQL Server estate via the Central Management Server (CMS) registration on the hub instance.
- Runs a 17-section read-only T-SQL assessment against each server, capturing configuration, security, schema, jobs, HA topology, and other migration-relevant metadata.
- Calculates a 1-year cost for each target: stay on-premises (DC-to-DC), Azure VM with Pay-As-You-Go SQL license, Azure VM with Bring-Your-Own-License (BYOL via Azure Hybrid Benefit), and Azure SQL Managed Instance.
- Calls Anthropic Claude (a large language model) to recommend a Managed Instance SKU and tier for each server, write a cost-versus-benefit narrative for each server, and synthesize an estate-wide migration strategy paragraph.
- Renders the result as an Excel workbook with an Executive Summary, an estate-wide Summary, a Methodology & Sources tab, a Critical Findings tab, a Remediation Plan tab, and one detailed tab per server.

### What this tool does NOT do

- It does not execute any migration. The assessment is read-only — it queries metadata, never modifies data.
- It does not access the actual database content. It looks at structure, configuration, and metadata only.
- It does not replace human judgment for production decisions. The AI narrative is reasoning support; the architect still owns the call.
- It does not include migration project costs (data transfer, application changes, licensing transition, dual-running, testing). The cost numbers are steady-state operational cost only.
- **It is not a fully autonomous AI agent.** It calls an LLM at three specific decision points within a deterministic pipeline. The agentic capabilities (planning loop, tool use, self-correction) are Phase 2 of this POC.

## 2. How to Read the Excel Report

The workbook has six categories of tabs. Read them in this order on first review:

### Tab 1: Executive Summary

Start here. This single tab answers "what does the estate look like, what should we do, and what will it cost." It contains four blocks:

- **Estate at a Glance** — six tiles: Servers Assessed, High Findings, Medium Findings, MI Ready, MI Conditional, MI Blocked. The High Findings tile and the MI Ready/Conditional/Blocked split are the two numbers a senior architect will look at first.
- **Top 3 Blockers** — the three most frequent High-severity finding categories across the estate, with the count of affected servers.
- **Per-Server Scoreboard** — one row per server: MI Readiness Score (0-100), label (Ready / Conditional / Blocked), High and Medium finding counts, and the top issue.
- **AI Estate Migration Strategy** — a 2-3 paragraph narrative auto-generated by Claude after analyzing all per-server recommendations.
- **1-Year Cost Summary by Migration Target** — every server with the four target costs and the AI-recommended target.

### Tab 2: How to Read This Report

A 60-second orientation embedded in the workbook itself. Companion to this guide.

### Tab 3: Summary

Per-server inventory + estate totals. Use this when someone asks "how big is the estate" or "give me a quick count of X across all servers."

### Tab 4: Critical Findings

A unified, sortable list of every High-severity finding across every server. Use when scoping remediation work.

### Tab 5: Remediation Plan

A pattern-matched mapping from each High finding to a recommended remediation step.

### Tab 6: Methodology & Sources

A defensibility tab. Six sections explaining where every cost number came from, what AI was used and for what, and what caveats apply. Read this once, fully, the first time you open the workbook.

### Tabs 7+: Per-Server Detail (one tab per server)

Each server gets its own tab. The structure of every per-server tab is identical:

- A green Migration Recommendation (AI-Driven) section at the top with the recommended target, AI narrative paragraph, four cost cards, and the AI-recommended MI SKU rationale.
- 17 sections of assessment data: Instance Summary, Instance Configuration, Linked Servers, SQL Agent Jobs, Database Inventory, DB-Level Findings, T-SQL Code Scan, Per-DB SKU Features, CLR Assemblies, Database Files, Availability Groups, Database Mirroring, Log Shipping (Primary and Secondary), Replication (Subscribers and Publishers), and a Cloud Migration Matrix at the bottom.
- Sections marked "(none)" are not absent — the agent checked and found nothing. This is intentional and is the right behavior for compliance review.

## 3. How the AI Component Works

The AI in this agent is intentionally bounded. Understanding what the AI does and does not do is essential to defending the report.

### What the AI is used for

- Recommending the right Azure SQL Managed Instance SKU per server (tier and vCore count) based on workload characteristics from the assessment data.
- Picking the recommended migration target per server (DC, Azure VM PAYG, Azure VM BYOL, or Azure SQL MI) and writing a 3-5 sentence cost-versus-benefit narrative explaining why.
- Synthesizing a 2-3 paragraph estate-wide migration strategy after every per-server recommendation has been made.

### What the AI is NOT used for

- **Cost calculations.** All dollar figures come from deterministic math against either the Azure Retail Prices API (for cloud targets) or industry-standard reference rates (for on-premises). The AI does not estimate prices.
- **Severity scoring.** Each finding's severity is rule-based and consistent across runs.
- **SQL queries.** The 17-section assessment is hand-written read-only T-SQL. The AI does not generate or modify queries.
- **Migration execution.** The agent does not move data, change configuration, or interact with target systems.

### Provider and model

The agent currently uses Anthropic Claude (Sonnet 4.5) via the public Anthropic API. The agent is provider-abstracted: switching to Azure OpenAI requires changing one variable and setting three environment variables. The methodology tab shows which provider was used for any given report run.

### AI cost per run

Approximately 17 LLM calls per 8-server run: 2 per server (MI sizing + recommendation) plus 1 estate-wide synthesis. Total cost: approximately $0.50 to $0.70 per run at current Anthropic API pricing.

### Why the AI narrative may read slightly differently between runs

Large language models are not perfectly deterministic. The same input will produce semantically equivalent but textually different output across runs. The recommendations themselves are stable — if the underlying findings and costs are the same, the AI will recommend the same target — but the narrative wording will vary. This is normal and expected behavior.

## 4. How Cost Numbers Are Calculated

Cost defensibility is the core of the report.

### Pricing data sources

| Migration Target | Pricing Source | Validation |
|---|---|---|
| DC-to-DC | Industry-standard reference rates: hardware refresh, colocation, operational labor, storage, SQL license. | Documented in the Methodology & Sources tab. Refresh quarterly. |
| Azure VM (PAYG) | Azure Retail Prices API (live, no auth required) for the base Windows VM hourly rate, plus per-edition SQL license add-on. | Cross-validated against the Azure Pricing Calculator. Within ~10%. |
| Azure VM (BYOL) | Same as PAYG without the SQL license add-on (assumes Azure Hybrid Benefit). | Same calculator validation. |
| Azure SQL MI | Azure Retail Prices API for per-instance hourly rate at AI-recommended vCore tier, plus storage at $0.1006/GB-month. | Cross-validated against Azure Pricing Calculator. Within $1. |

### What is NOT included in the cost numbers

- Reserved Instance discounts (typically 30-60% off PAYG with 1- or 3-year commit).
- Enterprise Agreement or Microsoft Customer Agreement negotiated discounts.
- Dev/Test pricing.
- Migration project cost (data transfer, application changes, dual-running, testing).
- Operational efficiency gains from PaaS (DBA labor savings on patching, backups, etc).

The numbers shown represent steady-state Pay-As-You-Go list pricing. **Real customer cost is typically 20-40% lower after discounts.** The agent surfaces the upper-bound list cost to ensure the architecture board sees the worst case, not the best case.

### Pricing freshness

Each report run fetches Azure pricing live from the Retail Prices API at the moment the report is generated. The exact fetch timestamp is captured in the Methodology & Sources tab and in the Executive Summary footer. Azure pricing changes monthly; for any decision that depends on these numbers, the report should be re-run within 90 days.

## 5. How to Interpret the AI Recommendations

The AI assigns each server one of four targets.

### DC-to-DC (stay on-premises, refresh hardware)

Recommended only when cloud migration is genuinely not appropriate — typically because of regulatory residency requirements, network constraints, or workload characteristics that don't match cloud economics. The AI rarely recommends DC-DC purely on cost grounds because cloud is usually cheaper at PAYG, let alone with discounts.

### Azure VM (PAYG)

Pay-As-You-Go: the SQL license is rolled into the hourly VM rate. Best for: customers who do not have existing SQL Server licenses, want to avoid managing license compliance, or are running short-term workloads. Typically the most expensive Azure option for paid editions.

### Azure VM (BYOL — Bring Your Own License)

Use existing on-prem SQL Server license via Azure Hybrid Benefit. Best for: customers with active Software Assurance who want to maximize the value of existing license investment. Typically 30-50% cheaper than PAYG for paid editions. For Developer Edition, PAYG and BYOL are equivalent because the license is free either way.

### Azure SQL Managed Instance

Microsoft's managed PaaS offering for SQL Server. Best for: workloads that fit within MI's feature set, where the customer values eliminating patching, backup, and HA management overhead. More expensive than IaaS in raw price but typically cheaper in total cost of ownership when DBA labor savings are factored in.

### MI Verdicts: Blocked / Conditional / Ready

A server is marked **MI-Blocked** when it has at least one feature that Azure SQL Managed Instance cannot support. The most common blockers in real estates:

- FileStream or FileTable in any database
- UNSAFE or EXTERNAL CLR assemblies
- SQL Agent jobs using subsystems MI does not support (CmdExec, PowerShell, SSIS)
- In-Memory OLTP features beyond what MI supports
- Linked servers using legacy drivers (SQLNCLI is the most common)

A "Blocked" verdict does not mean MI is impossible — it means MI is not feasible without remediation work.

A server is **MI-Conditional** when it has Medium-severity findings that may require attention but no hard blockers. Typically: Windows Auth users that need to be migrated to Entra ID, deprecated compatibility levels, or moderate operational footprint.

A server is **MI-Ready** when no significant blockers or conditional issues exist. The migration can be planned as a near-term lift to MI without major prerequisites.

## 6. Reading a Per-Server Tab in Detail

Open any per-server tab. Top to bottom, here is how to read it:

### The header banner

The blue banner at the top reads: "Server: NAME — MI Migration Assessment". This identifies the server and the assessment scope.

### Migration Recommendation (AI-Driven)

The green-bordered section. Three things to read:

- **Recommended Target** — appears in green. The AI's pick after weighing cost, blockers, and operational considerations.
- **AI Narrative** — 3-5 sentences explaining the recommendation. Cites specific findings, cost differences, and operational considerations. Regenerated each run; wording varies.
- **Cost Cards** — four cost cells (DC, AzVM PAYG, AzVM BYOL, AzMI), with the recommended one highlighted in green. The MI card shows the AI-recommended SKU.
- **MI Sizing Rationale** — a single italicized sentence explaining why the AI sized the MI instance the way it did.

### Sections 1-17 of the assessment

Below the recommendation block, every per-server tab has the same 17 sections in the same order. Sections that returned no data display "(none)" — meaning the agent looked and found nothing.

Quick guide to which sections matter most for which decisions:

- **Sections 1-2 (Instance Summary, sp_configure)** — basic identification and instance-level configuration.
- **Section 3 (Linked Servers)** — direct MI compatibility flag. Linked servers using SQLNCLI driver are a known migration friction point.
- **Section 4 (SQL Agent Jobs)** — the highest-frequency MI blocker in most estates.
- **Section 6 (DB-Level Findings)** — security findings.
- **Section 9 (CLR Assemblies)** — UNSAFE or EXTERNAL CLR is an MI blocker. SAFE CLR is generally fine.
- **Section 11 (Availability Groups)** — the HA topology that needs to be preserved or re-architected.
- **Section 15 (Cloud Migration Matrix)** — the seven-target compatibility matrix at the bottom. Yes/No verdict for each target. Conservative, rule-based view; does not factor in cost.

## 7. Anticipated Questions and Answers

### "How do we know the cost numbers are right?"

Cost numbers come from two sources: (1) the live Azure Retail Prices API for cloud targets, and (2) industry-standard reference rates for on-premises. Both are documented in the Methodology & Sources tab. The cloud numbers were cross-validated against the Azure Pricing Calculator at the time of report generation; MI cost matches the calculator within $1, VM cost matches within ~10%. The fetch timestamp is preserved in the report so freshness is verifiable.

### "What if Azure pricing changes after the report is generated?"

Azure pricing changes monthly. The report should be regenerated within 90 days for any decision that depends on the cost numbers. Each run fetches fresh pricing from the live API. The relative ordering between targets is stable; absolute dollars drift.

### "How do we know the AI is not hallucinating numbers?"

The AI is not asked to compute or estimate any number. The PowerShell agent passes the AI four specific cost numbers it has already computed deterministically; the AI is asked only to reason about which target is best given those numbers and the assessment findings. The AI cannot invent a price or change a number — it can only choose a target and write narrative about it.

### "Why does the AI recommend the same target for many servers?"

Because in many estates, similar findings produce similar conclusions. Differentiation happens at the per-server narrative level: read each tab and you will see different reasoning emphasis even for servers with the same recommendation. Uniformity at the recommendation level is not template behavior; it reflects estate uniformity.

### "What if the AI is wrong?"

The AI narrative is reasoning support, not the final word. The architect retains authority for any production decision. The recommendation can be overridden, and any manual override should be documented in the customer-facing migration plan.

### "Can this scale to a 500-server estate?"

Yes, with caveats. The agent is currently sequential (~5-10 seconds per server). Production scale would require parallelization, batching of LLM calls, and potentially replacing Excel output with a database-backed reporting layer.

### "Where does customer data go?"

When using the current Anthropic Claude API integration, the assessment findings (server names, finding text, cost numbers) are sent to Anthropic over HTTPS. Anthropic's API terms state they do not train on customer API data. For deployments where data residency is a strict requirement, the agent supports Azure OpenAI as a drop-in replacement, in which case the data stays inside the customer's Azure tenant.

## 8. Known Limitations

Stated honestly:

### Cost methodology

- Uses PAYG list pricing. Actual customer cost is typically lower with Reserved Instances, Azure Hybrid Benefit, Enterprise Agreement, or Dev/Test pricing.
- On-prem reference rates are industry estimates. Actual customer on-prem cost varies significantly.
- Migration project cost is excluded — the numbers are steady-state operational only.

### AI behavior

- Narratives are non-deterministic — wording varies between runs even with identical input.
- The AI follows the prompt rules in the agent code; if the prompt is wrong, the AI reasoning will follow the wrong rules.
- The AI cannot access information outside what is passed to it in the prompt.

### Assessment scope

- SQL Server only. Oracle, PostgreSQL, MySQL, NoSQL engines are out of scope.
- Azure-first. AWS and GCP are evaluated for compatibility but not priced.
- Read-only metadata. The agent does not analyze actual database content or workload telemetry.

### Operational scope

- Sequential execution.
- Excel as output format.
- No persistence between runs.

## 9. How to Use the Report in a Decision Meeting

Suggested flow for a 30-minute architecture review meeting using this report.

### First 5 minutes: Frame the estate

Open the Executive Summary tab. Read the Estate at a Glance tiles aloud. Read the AI Estate Migration Strategy paragraph aloud.

### Next 10 minutes: Walk the cost summary

Scroll to the 1-Year Cost Summary table. For each server, name the recommended target and the cost. Pause on outliers.

### Next 10 minutes: Pick one or two servers and drill in

Open the per-server tab for the most complex server. Read the Migration Recommendation block, then scan the 17 sections to verify the AI's reasoning matches the underlying findings.

### Last 5 minutes: Capture decisions and remediations

Open the Remediation Plan tab. Identify the High findings that block the most servers — these are the highest-leverage remediation candidates.
